# BLE Advertising – Zusammenfassung

Zusammenfassung eines Chats zu Bluetooth Low Energy (BLE) Advertising, insbesondere im Kontext von Zephyr / nRF Connect SDK auf dem nRF52840 DK.

---

## 1. BR/EDR not supported

- **BR** = Basic Rate, **EDR** = Enhanced Data Rate → zusammen "Bluetooth Classic"
- "BR/EDR not supported" bedeutet: Das Gerät unterstützt **nur BLE (Bluetooth Low Energy)**, kein klassisches Bluetooth.
- Praktische Folge: Klassische Audio-Profile (z. B. A2DP für Kopfhörer, HFP/HSP) funktionieren nicht – typisch für Beacons, Fitness-Tracker, Sensoren.
- Dieses Flag kommt aus dem **Flags-AD-Type** (siehe unten), Bit 2 (`0x04`).

---

## 2. Advertising Data (AD) – Struktur eines Pakets

Ein Advertising-Paket besteht aus mehreren **AD-Strukturen** im Format:

```
[Length][Type][Data...]
```

### Beispiel aus dem Log (`bt_data_parse`)

```
ad[0]: type=1, len=1        → Flags: 0x04 (BR/EDR not supported, LE only)
ad[1]: type=9, len=13       → Complete Local Name: "Nordic_Beacon"
```

### Wichtige AD-Types

| Type (hex) | Name | Bedeutung |
|---|---|---|
| 0x01 | Flags | LE Discoverable Mode, BR/EDR-Support |
| 0x08 / 0x09 | Shortened / Complete Local Name | Gerätename |
| 0x02/0x03, 0x06/0x07 | Service UUID Lists (16-/128-bit) | Angebotene Services |
| 0x16 / 0x21 | Service Data (16-/128-bit UUID) | Daten zu einem Service (z. B. Eddystone) |
| 0xFF | Manufacturer Specific Data | Herstellerspezifisch, beginnt mit 2-Byte Company ID (z. B. iBeacon) |
| 0x0A | Tx Power Level | Sendeleistung in dBm |
| 0x1A | Advertising Interval | Advertising-Häufigkeit |

Definiert in: `zephyr/include/zephyr/bluetooth/gap.h`

---

## 3. 31-Byte-Limit & Lösungen für mehr Daten

Ein **Legacy Advertising Paket** hat max. **31 Bytes** für AD-Daten.

| Bedarf | Lösung |
|---|---|
| Bis zu 62 Bytes gesamt, Legacy-kompatibel | **Scan Response** (zweites 31-Byte-Paket, wird nur bei Active Scan übertragen) |
| Deutlich mehr Platz (bis 255 Bytes+), nur BT 5.0+ Empfänger | **Extended Advertising** (`BT_LE_ADV_OPT_EXT_ADV`) |
| Große/variable Datenmengen | **GATT-Verbindung** nutzen statt alles im Advertising zu senden |

### Beispiel: 3 AD-Strukturen unter 31 Bytes

```c
#define COMPANY_ID_CODE 0x0059  // Nordic Semiconductor

typedef struct {
    uint16_t company_id;
    int16_t  temperature;
    uint8_t  battery_pct;
    uint8_t  reserved;
} mfg_data_t;

static mfg_data_t mfg_data = {
    .company_id  = COMPANY_ID_CODE,
    .temperature = 2350,
    .battery_pct = 87,
    .reserved    = 0x00,
};

static const struct bt_data ad[] = {
    BT_DATA_BYTES(BT_DATA_FLAGS, BT_LE_AD_NO_BREDR),
    BT_DATA(BT_DATA_MANUFACTURER_DATA, (uint8_t *)&mfg_data, sizeof(mfg_data)),
    BT_DATA(BT_DATA_NAME_COMPLETE, "Nordic_Beacon", 13),
};
```

→ Gesamtgröße: 26 Bytes (passt in 31 Bytes)

## 4. Company Identifier (Bluetooth SIG)

- Wird von der Bluetooth SIG an Mitgliedsfirmen vergeben, für `Manufacturer Specific Data` (Type 0xFF).
- Offizielle Liste: https://www.bluetooth.com/specifications/assigned-numbers/company-identifiers
- Community-Spiegel: https://github.com/NordicSemiconductor/bluetooth-numbers-database
- Nordic Semiconductor Company ID: `0x0059`

## 5. Zwei verschiedene "Advertising Type"-Konzepte

### a) AD-Type (Host-Ebene, `struct bt_data.type`)

- Betrifft einzelne Datenfelder im Paket (Flags, Name, Manufacturer Data, ...)
- Gesetzt: im App-Code beim Bauen des `ad[]`-Arrays (Senden) bzw. von `bt_data_parse()` beim Empfangen
- Printbar: direkt im eigenen Parse-Callback (`data->type`)

### b) PDU-Type (Link-Layer-Ebene, Advertising-Channel-PDU-Header)

- Bestimmt, ob das Paket **verbindbar** und/oder **scanbar** ist
- Werte: `ADV_IND`, `ADV_DIRECT_IND`, `ADV_NONCONN_IND`, `ADV_SCAN_IND`
- Definiert in: `zephyr/subsys/bluetooth/controller/ll_sw/pdu.h` (struct `pdu_adv`, 4-Bit-Feld `type`)
- Gesetzt: in `ll_adv_params_set()` (`ull_adv.c`) – **nur wenn der Open-Source Zephyr-Controller genutzt wird** (`CONFIG_BT_LL_SW_SPLIT=y`)
- **Wichtig für nRF52840 DK:** Standardmäßig läuft der **SoftDevice Controller (SDC)** von Nordic (`CONFIG_BT_LL_SOFTDEVICE=y`), eine Closed-Source-Bibliothek – dort ist der Quellcode nicht einsehbar und man kann keinen `printk` einbauen.
- Printbar: am einfachsten über den **Scan-Callback** beim Empfangen (nicht durch Debuggen des Senders):

```c
static void scan_cb(const bt_addr_le_t *addr, int8_t rssi,
                     uint8_t adv_type, struct net_buf_simple *buf)
{
    printk("adv_type = 0x%02x\n", adv_type);
}
```

Alternativ: **nRF Sniffer for Bluetooth LE** (Wireshark-Plugin) zeigt den PDU-Type im Raw-Air-Traffic an.

## 6. `bt_le_adv_param` – wie er den PDU-Type bestimmt

```c
struct bt_le_adv_param {
    uint8_t  id;
    uint8_t  sid;
    uint32_t options;
    uint32_t interval_min;
    uint32_t interval_max;
    const bt_addr_le_t *peer;
};
```

### Entscheidungstabelle

| `BT_LE_ADV_OPT_CONNECTABLE` | `peer` | Scan Response (`sd`) übergeben? | Resultierender PDU-Type |
|---|---|---|---|
| gesetzt | `NULL` | – | `ADV_IND` |
| gesetzt | gesetzt | – | `ADV_DIRECT_IND` |
| nicht gesetzt | `NULL` | Nein | `ADV_NONCONN_IND` |
| nicht gesetzt | `NULL` | **Ja** | `ADV_SCAN_IND` |

### Vordefinierte Makros

```c
#define BT_LE_ADV_CONN  BT_LE_ADV_PARAM(BT_LE_ADV_OPT_CONNECTABLE, ...)   // → ADV_IND
#define BT_LE_ADV_NCONN BT_LE_ADV_PARAM(0, ...)                          // → ADV_NONCONN_IND (ohne sd)
```

`BT_GAP_ADV_FAST_INT_MIN_2` / `MAX_2` = 100 ms / 150 ms ("Fast Advertising, Set 2"), Einheit: 0.625-ms-Schritte.

---

## 7. `BT_LE_ADV_OPT_USE_IDENTITY`

- Betrifft **nicht** den PDU-Type, sondern die **gesendete Adresse**:
  - **Ohne** Option: RPA (Resolvable Private Address) – rotiert periodisch (Privacy-Schutz)
  - **Mit** Option: feste Identity Address (Public oder Static Random) – bleibt über Neustarts gleich
- Typischer Einsatz: Beacons/Dev-Boards, bei denen eine wiedererkennbare, feste Adresse gewünscht ist (z. B. für Debugging oder Asset-Tracking).

---

## 8. Konkrete Analyse: `adv_param` im Chat-Beispiel

```c
adv_param = BT_LE_ADV_PARAM(BT_LE_ADV_OPT_USE_IDENTITY,
                             BT_GAP_ADV_FAST_INT_MIN_2,
                             BT_GAP_ADV_FAST_INT_MAX_2,
                             NULL);

err = bt_le_adv_start(adv_param, ad, ARRAY_SIZE(ad), sd, ARRAY_SIZE(sd));
```

**Auswertung:**

| Bedingung                            | Status        |
| ------------------------------------ | ------------- |
| `BT_LE_ADV_OPT_CONNECTABLE` gesetzt? | Nein          |
| `peer` übergeben?                    | Nein (`NULL`) |
| `sd` (Scan Response) vorhanden?      | **Ja**        |

→ **Resultierender PDU-Type: `ADV_SCAN_IND`**
(nicht verbindbar, aber scanbar – Scanner können per `SCAN_REQ` die `sd`-Daten als `SCAN_RSP` abrufen)

→ **Adresse:** feste Identity Address (wegen `USE_IDENTITY`), keine rotierende RPA

→ **Intervall:** 100–150 ms (Fast Advertising, Set 2)
